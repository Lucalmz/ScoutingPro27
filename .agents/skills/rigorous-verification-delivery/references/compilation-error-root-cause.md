# 编译错误根因盘查与防敷衍指南 (Compilation Error Root Cause Investigation)

在日常开发中，**"小编译错误 90% 潜藏着大 Bug"**。很多时候，编译器报错只是表象，暴露出的是深层的设计分歧、契约断裂或上游变更遗漏。

---

## 1. 为什么"消灭编译错误"是最危险的操作？

AI 常见的敷衍修复模式（Anti-Patterns）：
- **盲目类型强转**：`(String) obj` 或 `as any`，强行让类型系统通过，运行时直接抛 `ClassCastException` / `TypeError`。
- **填补 Dummy/默认参数**：方法缺参数时，顺手传 `null`, `0`, `""` 或 `false`，导致下游业务逻辑静默走入错误分支。
- **草率修改方法签名**：看到编译报错直接去改公共接口的入参/返回值，导致其它 10 个未直接报错的调用方逻辑全部被带偏。
- **吞掉/降级异常**：用空的 `catch (Exception e) {}` 消除 `Unhandled exception` 编译报错，导致系统在崩溃时毫无日志。

```
[表面现象] 编译器报错: Method signature mismatch / Type error
   │
   ├── ❌ 敷衍修复: 强转、塞 null、改单行、让编译器闭嘴
   │       └── 结果: 埋下隐蔽的运行时崩溃、数据脏写或业务逻辑断裂 (90% 大 Bug)
   │
   └── ✅ 严谨盘查: 追溯上游改动 -> 还原完整业务契约 -> 广度扫描所有调用点 -> 彻底修复
```

---

## 2. 编译错误根因盘查三步法 (The 3-Step Root Cause Audit)

一旦遭遇编译错误，**严禁立即动手修改当前报错行**，必须按以下三步执行盘查：

### 第一步：溯源 (Trace Origin)
- 这个方法/字段/类型为什么会发生变化？
- 是谁、在哪一次改动中调整了签名或数据结构？
- 这次变更背后的真实业务意图是什么？（是重构、废弃、新增字段还是架构拆分？）

### 第二步：广度扫描 (Breadth Scan)
- 除了当前报错的文件，项目中还有哪些地方调用了该方法/使用了该结构？
- 前后端通信 JSON 字段、数据库映射字段、缓存序列化是否受到影响？
- 是否有重载方法（Overload）或接口实现类未同步更新？

### 第三步：深度契约修复与逻辑复核 (Deep Contract Repair)
- 按照完整的业务契约进行修复，确保每一个入参都有合法的业务来源，每一个返回值都被正确消费。
- 检查修改是否破坏了前置条件（Preconditions）、后置条件（Postconditions）与并发/状态不变量。

## 3. 典型案例对比

### 案例：后端 Service 接口新增了 `userId` 参数以支持多租户

- **错误做法（头痛医头）**：
  看到 Controller 编译报错 `login(username, password)` 缺少参数，随手写 `login(username, password, null)` 或 `login(username, password, "admin")`。
  *后果*：非管理员用户登录后全部被归为 admin 或因为 null 引发空指针，造成严重越权漏洞。

- **正确做法（深度盘查）**：
  1. 识别出 `userId` 是多租户安全升级必需的上下文。
  2. 检查从 Session / JWT Token 中提取 `userId` 的完整链路。
  3. 将上下文正确传递给 Controller 并喂入 Service。
  4. 扫描全局所有调用 `login()` 的位置（单元测试、后台定时任务、内部 API）并统一补全真实上下文。
